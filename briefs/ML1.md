## Что получаем на выходе и как это стыкуется

После обоих брифов у команды есть **работающий сквозной сценарий на синтетике**: семья с чеками → агент решает, что ей показать и почему → движок считает рост, лигу и скор → экраны и чек показывают реальные числа из симуляции. Завтра можно показать одну семью насквозь.

| Кто | Что получается | Какой пункт кейса закрывает |
|---|---|---|
| ML-1 | Синтетическая аудитория приложения с реальными долями сегментов X5 и 12 неделями чеков | фундамент для всего; честный ответ на «синтетика манипулятивна»: доли настоящие, поведение модель |
| ML-1 | Агент: тип по чекам → первая механика → объяснение для пользователя и продакта → челлендж недели | персональный челлендж из истории, механизм рекомендации механики, объяснение выбора |
| ML-1 | Мини-eval на 30 профилях с процентом попаданий и худшими примерами | критерий «релевантность ≥70%», с честной пометкой про выборку |
| ML-2 | Движок правил + rules.md на страницу | правила начисления и экономика наград |
| ML-2 | Симуляция 8 недель: ростомеры, лиги, разрыв до топ-3, спасённое | обновление прогресса аватара и места в рейтинге; симуляция на 1–10 тыс. пользователей; проверка H3 |
| ML-2 | Антифрод v0: скор, три кейса, объяснимый порог | «простой скоринг, precision важнее recall, порог объясним» |
| ML-2 | Прототип 4 экранов для двух семей + макет чека | кликабельный прототип 3–4 экрана; вау-элемент для встречи |

**Стыковка:** `data/` от ML-1 → `ai/out/challenges.jsonl` от ML-1 → `sim/` ML-2 читает и то и другое → `sim/out/` даёт числа для `proto/`. До готовности данных ML-2 работает на заглушке из 200 семей той же схемы.

**Чего на выходе не будет, и это нормально для чек-поинта:** доказательства аплифта частоты (в симуляцию сознательно не закладываем), настоящей печати на кассе, интеграций, ответа на каннибализацию уценки. Аплифт и каннибализация живут в экономической модели Ивана как допущения с чувствительностью.

## Задача 1. Генератор синтетических семей и чеков

**Зачем:** на этих данных работают агент, симуляция и прототип; доли сегментов у нас реальные от X5, поведение внутри — модель. Так и маркируем.

**Вход:** файл `данные профиля клиентов_.md` — доли пяти сегментов по трём сетям, отдельно для пользователей приложения. Берём распределение «пользователи МП».

**Выход:**
- `data/profiles.csv` — 2 000–10 000 пользователей, сгруппированных в семьи.
- `data/receipts.csv` и `data/receipt_items.csv` — 12 недель истории.
- `data/README.md` — что реальное, что допущение, источники калибровки.

**Схема `profiles.csv`:**

| Поле | Тип | Как задаётся |
|---|---|---|
| user_id, family_id | str | семья = 1–3 взрослых с одной card_id |
| network_home | TS5 / TSX / TSCH | доля магазинов: Пятёрочка ≈ 70%, Перекрёсток ≈ 10%, Чижик ≈ 20% — допущение |
| x5_segment | молодёжь / вредные привычки / дети до 3 / зрелые / старшие | реальные доли МП по сети из файла X5 |
| is_app_user | bool | все true, генерируем только аудиторию приложения |
| behavior_type | хозяин / охотник / категорийный | допущение: 50 / 30 / 20 внутри семей с детьми; у остальных сегментов 60 / 30 / 10. 🟡 Сами три типа — гипотеза на репликах кейсодателя, не данные X5 (CONCEPT.md §4); сделай их списком в конфиге, чтобы заменить на сегментацию X5, если она найдётся |
| child_stage | none / 0-6 / 6-9 / 9-12 / 1-2 / 2-3 | только у сегмента «дети до 3», равномерно; у остальных none |
| city_bucket | 1–20 | равномерно |
| base_freq_per_week | float | семьи с детьми 1,5–3; молодёжь 0,5–1,5; зрелые 1–2; старшие 2–4 — допущение |
| avg_check_rub | float | ориентир по сетям 564 / 878 / 711 ₽ (вторичные источники по отчётности X5, 2 кв. 2026); семьи +20% |
| promo_share, markdown_share | float | по типу: хозяин 0,3 / 0,05; охотник 0,5 / 0,25; категорийный 0,3 / 0,05 |
| top_categories | list | из таксономии ниже, у семей обязательно детские категории |

**Таксономия категорий (≈30):** молочка, кефир/йогурты, творог, хлеб, овощи, фрукты, мясо, курица, рыба, крупы, макароны, консервы, готовая еда, выпечка, снеки, напитки, кофе/чай, сладкое, замороженное, бытовая химия, гигиена, **подгузники, детское пюре, детские каши, детские творожки, заменители грудного молока (исключено), детская гигиена**, алкоголь (исключено), табак (исключено).

**Схема `receipt_items.csv`:** receipt_id, sku, category, qty, price_shelf, price_paid, is_promo, is_markdown, is_excluded. Уценка: скидка 30–50%, только в категориях молочка, хлеб, овощи, фрукты, готовая еда, выпечка. Детское питание с is_markdown = false всегда.

**Критерии приёмки:** доли сегментов в выборке совпадают с файлом X5 с точностью ±1 п.п.; у семей с детьми средний чек и частота выше остальных; у «охотников» доля уценки заметно выше; ни одного чека с уценённым детским питанием; README с таблицей «реальное / допущение».

## Задача 2. LLM-агент: тип, рекомендация механики, челлендж недели

**Вход:** профиль пользователя, child_stage, чеки семьи за 8 недель, список исключённых категорий, список уценки в домашнем магазине на неделю (из синтетики).

**Выход** — JSON строго такой схемы:

```json
{
  "user_id": "u_000123",
  "behavior_type": "хозяин | охотник | категорийный",
  "type_evidence": "1–2 фразы: какие признаки в чеках",
  "mechanic_first": "rostomer | save_product | stage_mission",
  "mechanic_explanation_user": "одна фраза для пользователя, обращение к родителю",
  "mechanic_explanation_product": "одна фраза для продакта лояльности",
  "challenge": {
    "week": "2026-W37",
    "habitual_items": [
      {"category": "молочка", "expected_saving_rub": 60, "why": "каждую неделю в чеках"}
    ],
    "stage_mission": {"name": "Первая ложка", "items": ["детское пюре кабачок"], "stage": "6-9"},
    "markdown_categories": ["кефир/йогурты"],
    "target_saving_rub": 180
  },
  "constraints_checked": {"no_excluded": true, "no_baby_food_markdown": true, "stage_matches": true}
}
```

**Ограничения в промпте:** не предлагать то, чего семья не покупает; заменители грудного молока и питание первого года не предлагать никогда; детское питание не из уценки; для этапа 0–6 и none — без миссии этапа; обращение к родителю, не к ребёнку; ответ по-русски.

**Технически:** любой доступный LLM API, промпт в `ai/prompts/challenge.md`, код в `ai/challenge_agent.py`, запуск на 30 профилях батчем, результаты в `ai/out/challenges.jsonl`. Правила из CONCEPT.md §3 модель не считает — только выбирает и объясняет.

**Критерии приёмки:** 30 JSON валидны по схеме; constraints_checked все true; для трёх типов первый экран отличается; у 30 профилей нет двух одинаковых челленджей.

## Задача 3. Мини-eval релевантности

**Метод:** LLM-as-judge по рубрике + ручная проверка 10 профилей Иваном. Попадание = все habitual_items из топ-5 категорий семьи по чекам И миссия соответствует этапу И нет исключённых категорий И оценщик согласен «это про нас».

**Выход:** `ai/out/eval.md` — таблица 30 строк (user_id, тип, попадание да/нет, комментарий), процент попаданий, 5 лучших и 3 худших примера для слайда. Честная пометка: выборка 30, синтетика.

**Критерий приёмки:** таблица есть, процент посчитан, худшие примеры не спрятаны.
